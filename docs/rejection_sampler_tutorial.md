## 1. 背景知识

### 1.1 为什么需要投机解码？

大语言模型（LLM）推理的主要瓶颈是**内存带宽**而非计算能力。每次生成一个 token 时，模型需要从显存中读取全部参数，但只产生一个 token 的输出。这就像用一辆大卡车运送一个苹果——效率很低。

```
传统自回归生成：
┌─────────────────────────────────────────────────────┐
│  时间步 1: 读入全部参数 → 生成 token 1              │
│  时间步 2: 读入全部参数 → 生成 token 2              │
│  时间步 3: 读入全部参数 → 生成 token 3              │
│  ...                                                │
│  每次都要"搬运"整个模型，但只产出1个token           │
└─────────────────────────────────────────────────────┘
```

### 1.2 投机解码的解决思路

**核心思想**：用一个小而快的"草稿模型"（Draft Model）先生成多个候选 token，然后用大模型并行验证这些 token。

```
投机解码：
┌─────────────────────────────────────────────────────┐
│  步骤1: Draft模型快速生成 k 个候选tokens            │
│         [token1, token2, token3, ...]               │
│                                                     │
│  步骤2: Target模型一次性验证所有候选tokens          │
│         ✓ token1 匹配                               │
│         ✓ token2 匹配                               │
│         ✗ token3 不匹配 → 拒绝                      │
│                                                     │
│  结果: 接受2个token，只用了1次大模型推理            │
└─────────────────────────────────────────────────────┘
```

**优势**：
- 如果草稿模型的猜测大部分正确，可以显著提高吞吐量
- 即使猜测错误，也能保证输出质量与大模型相同

## 2. 名词解释

| 术语 | 英文 | 解释 |
|------|------|------|
| **Draft Model** | 草稿模型 | 一个小而快的模型，用于快速生成候选 token。通常比 Target Model 小很多（如 7B vs 70B） |
| **Target Model** | 目标模型 | 我们真正想要使用的大模型，负责验证 Draft Model 的输出 |
| **Speculative Decoding** | 投机解码 | 使用 Draft Model 预测 + Target Model 验证的解码策略 |
| **Rejection Sampling** | 拒绝采样 | 一种采样方法，根据概率决定接受或拒绝候选 token |
| **Draft Token** | 草稿 Token | Draft Model 生成的候选 token |
| **Bonus Token** | 奖励 Token | 当所有 Draft Token 都被接受时，额外生成的一个 token |
| **Recovered Token** | 恢复 Token | 当 Draft Token 被拒绝时，从修正分布中采样的 token |
| **Greedy Sampling** | 贪婪采样 | 每次选择概率最高的 token（确定性） |
| **Random Sampling** | 随机采样 | 根据概率分布随机选择 token（有随机性） |
| **Temperature** | 温度 | 控制采样随机性的参数。温度越高越随机，越低越确定 |
| **Top-k** | 前 k 采样 | 只从概率最高的 k 个 token 中采样 |
| **Top-p** | 核采样 | 只从累积概率达到 p 的最小 token 集合中采样 |
| **N-gram** | N元语法 | 一种基于统计的简单预测方法，不需要 Draft Model |
| **Block Verify** | 块验证 | MagicMTP 论文提出的方法，使用累积乘积提高接受率 |
| **Logits** | 未归一化概率 | 模型输出的原始分数，经过 softmax 后变成概率 |
| **Vocabulary Size** | 词表大小 | 模型能识别的所有 token 的数量（如 32000, 128000） |

## 3. 投机解码原理

### 3.1 基本流程图

```
┌─────────────────────────────────────────────────────────────────┐
│                    投机解码完整流程                              │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  第一步：Draft Model 生成候选序列                                │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  输入: "今天天气"                                           │  │
│  │  Draft Model 快速生成: ["很", "好", "，"]                   │  │
│  │  同时记录每个 token 的概率: p_draft(["很"]), p_draft(["好"]) │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  第二步：Target Model 并行验证                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  输入: "今天天气很"，"今天天气很好"，"今天天气很好，"        │  │
│  │  Target Model 一次性计算所有位置的 logits                   │  │
│  │  得到: p_target(["很"]), p_target(["好"]), p_target(["，"]) │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  第三步：拒绝采样验证                                            │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  对每个 draft token 计算接受概率:                           │  │
│  │  accept_prob = min(1, p_target / p_draft)                  │  │
│  │                                                            │  │
│  │  生成随机数 u ~ Uniform(0,1)                               │  │
│  │  如果 u < accept_prob → 接受该 token                       │  │
│  │  否则 → 拒绝该 token，使用 recovered token 替代             │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  第四步：输出最终序列                                            │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  如果全部接受: 返回 ["很", "好", "，"] + bonus_token        │  │
│  │  如果部分接受: 返回 [接受的tokens] + recovered_token        │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 为什么需要拒绝采样？

你可能会问：为什么不直接比较 Draft Token 和 Target Model 的输出是否相同？

**答案是**：这只适用于贪婪采样（Greedy Sampling），但不适用于随机采样。

#### 贪婪采样的简单情况

```
Draft 预测:  "很" (概率最高)
Target 验证: "很" (概率最高)
→ 匹配，接受！
```

#### 随机采样的复杂情况

```
Draft 分布:  {"很": 0.6, "非": 0.3, "挺": 0.1}
Target 分布: {"很": 0.5, "非": 0.4, "挺": 0.1}

Draft 选择了 "很"，但 Target 的分布略有不同。
如何判断是否应该接受？

答案：使用拒绝采样！
```

## 4. 拒绝采样算法

### 4.1 数学原理

拒绝采样的核心是确保最终输出**完全符合 Target Model 的分布**。

**接受概率公式**：
```
accept_prob(x) = min(1, p_target(x) / p_draft(x))
```

**直观理解**：
- 如果 `p_target(x) >= p_draft(x)`：接受概率为 1（Target 比 Draft 更喜欢这个 token）
- 如果 `p_target(x) < p_draft(x)`：接受概率小于 1（Draft 比 Target 更喜欢这个 token）

### 4.2 两种采样模式对比

#### 贪婪采样模式

```
┌────────────────────────────────────────────────────────────┐
│  贪婪采样拒绝采样                                           │
│                                                            │
│  Draft tokens:  [A, B, C, D]                               │
│  Target argmax: [A, B, X, D]                               │
│                     ↑                                      │
│                  不匹配！                                   │
│                                                            │
│  处理逻辑:                                                  │
│  1. 位置0: A == A → 接受，填入 target[A]                   │
│  2. 位置1: B == B → 接受，填入 target[B]                   │
│  3. 位置2: C != X → 拒绝，填入 target[X]                   │
│  4. 位置3: D → 跳过（因为前面已经拒绝）                     │
│                                                            │
│  最终输出: [A, B, X, -1]    ← 无 bonus，因为有不匹配        │
│                                                            │
│  ────────────────────────────────────────────────────────  │
│                                                            │
│  另一个例子（全部匹配）:                                    │
│  Draft tokens:  [A, B, C]                                  │
│  Target argmax: [A, B, C]                                  │
│                                                            │
│  处理逻辑:                                                  │
│  1. 位置0: A == A → 接受                                   │
│  2. 位置1: B == B → 接受                                   │
│  3. 位置2: C == C → 接受                                   │
│                                                            │
│  最终输出: [A, B, C, bonus] ← 全部接受，追加 bonus          │
│                                                            │
│  ★ 关键规则: bonus token 仅当所有 draft tokens 都被接受    │
│             （即 first_mismatch_pos >= draft_tokens数量）  │
│             时才添加！                                     │
└────────────────────────────────────────────────────────────┘
```

#### 随机采样模式

```
┌────────────────────────────────────────────────────────────┐
│  随机采样拒绝采样                                           │
│                                                            │
│  Draft token: A                                            │
│  p_draft(A) = 0.8                                          │
│  p_target(A) = 0.6                                         │
│                                                            │
│  接受概率 = min(1, 0.6/0.8) = 0.75                         │
│                                                            │
│  生成随机数 u = 0.3                                        │
│  0.3 < 0.75 → 接受！                                       │
│                                                            │
│  ────────────────────────────────────────────────────────  │
│                                                            │
│  另一个例子:                                                │
│  Draft token: B                                            │
│  p_draft(B) = 0.9                                          │
│  p_target(B) = 0.3                                         │
│                                                            │
│  接受概率 = min(1, 0.3/0.9) = 0.33                         │
│                                                            │
│  生成随机数 u = 0.7                                        │
│  0.7 >= 0.33 → 拒绝！使用 recovered token                  │
└────────────────────────────────────────────────────────────┘
```

### 4.3 恢复分布（Recovery Distribution）

当 Draft Token 被拒绝时，我们需要从修正后的分布中采样一个 token：

```
修正分布: p_recover(x) = max(0, p_target(x) - p_draft(x)) / Z

其中 Z 是归一化常数
```

**为什么要用这个分布？**

1. 它确保我们不会重复采样 Draft 已经高概率生成的 token
2. 它保证最终分布与 Target Model 完全一致

```
例子：
┌─────────────────────────────────────────────────────────────┐
│  Token  │ p_draft │ p_target │ p_recover = max(0, diff)    │
│────────┼─────────┼──────────┼─────────────────────────────│
│  A     │  0.8    │  0.6     │  0.0 (Draft 更喜欢 A)       │
│  B     │  0.1    │  0.3     │  0.2 (Target 更喜欢 B)      │
│  C     │  0.1    │  0.1     │  0.0 (相同)                 │
└─────────────────────────────────────────────────────────────┘

从 p_recover 采样，更可能选择 B
```

### 4.4 Block Verify（块验证）

Block Verify 是 MagicMTP（Magic Multi-Token Prediction）论文提出的一种改进方法。

**传统方法**：逐个验证每个 token
```
位置0: accept_prob >= u[0] ?
位置1: accept_prob >= u[1] ?
位置2: accept_prob >= u[2] ?
```

**Block Verify**：使用累积乘积一次性验证
```
接受前 k 个 token 的条件：
∏(i=0 to k) π_i >= ∏(i=0 to k) u_i

其中 π_i = min(1, p_target/p_draft)
```

**数据流对比**：
```
传统方法：
位置:      [0]     [1]     [2]
π:         [0.9]   [0.8]   [0.95]
u:         [0.5]   [0.7]   [0.6]
接受:      [✓]     [✓]     [✓]

Block Verify:
位置:      [0]     [1]     [2]
π:         [0.9]   [0.8]   [0.95]
累积π:     [0.9]   [0.72]  [0.684]   ← 逐位相乘
u:         [0.5]   [0.7]   [0.6]
累积u:     [0.5]   [0.35]  [0.21]    ← 逐位相乘
接受:      [✓]     [✓]     [✓]       ← 累积π >= 累积u
```

## 5. 代码实现解析

### 5.1 核心函数调用关系

```
rejection_sample()                        # 主入口函数
├── apply_sampling_constraints()          # 应用温度、top-k、top-p
├── 贪婪采样路径 (not all_random)
│   ├── rejection_greedy_sample_spec_len_1_pytorch()  # 特殊优化: spec_len=1
│   │   └── 简化逻辑，直接比较
│   └── rejection_greedy_sample_pytorch() # 通用贪婪采样
│       └── 比较draft和target的argmax
├── sample_recovered_tokens()             # 预计算恢复token
│   └── sample_recovered_tokens_pytorch()
│       └── Gumbel-max采样
├── rejection_random_sample_pytorch()     # 随机采样路径（传统，spec_len<3）
│   └── 逐个验证
└── rejection_random_sample_block_verify_pytorch()  # 随机采样路径（Block Verify，spec_len>=3）
    └── 累积乘积验证
```

**特殊优化路径说明**：

| 条件 | 使用函数 | 说明 |
|------|----------|------|
| `min(num_draft_tokens)==1 && max(num_draft_tokens)==1 && all_greedy` | `rejection_greedy_sample_spec_len_1_pytorch` | 每个请求只有1个draft token且全部贪婪采样时的优化 |
| `max_spec_len >= 3` | `rejection_random_sample_block_verify_pytorch` | 使用 Block Verify 提高接受率 |
| `max_spec_len < 3` | `rejection_random_sample_pytorch` | 传统逐个验证 |

### 5.2 关键数据结构

```python
# 输入数据
draft_token_ids:    [num_tokens]           # 展平的所有draft tokens
num_draft_tokens:   [batch_size]           # 每个请求的draft数量
cu_num_draft_tokens: [batch_size]          # 累积draft数量（前缀和）
draft_probs:        [num_tokens, vocab]    # draft概率分布
target_logits:      [num_tokens, vocab]    # target的logits
bonus_token_ids:    [batch_size, 1]        # bonus tokens

# 输出数据
output_token_ids:   [batch_size, max_spec_len+1]  # 最终输出的tokens
```

### 5.3 批处理示例

```
假设 batch_size=2, max_spec_len=4

请求0: draft生成了3个tokens [10, 20, 30]
请求1: draft生成了2个tokens [40, 50]

数据布局：
───────────────────────────────────────────────────
draft_token_ids:     [10, 20, 30, 40, 50]
                       ↑────────↑  ↑───↑
                       请求0       请求1

num_draft_tokens:    [3, 2]
cu_num_draft_tokens: [3, 5]    ← 前缀和

output_token_ids (初始):
───────────────────────────────────────────────────
请求0: [-1, -1, -1, -1, -1]    ← 5列 (max_spec_len+1)
请求1: [-1, -1, -1, -1, -1]

处理后的output_token_ids:
───────────────────────────────────────────────────
请求0: [10, 20, recovered, -1, -1]   ← 位置2被拒绝
请求1: [40, 50, bonus, -1, -1]       ← 全部接受，追加bonus
```

### 6.2 随机采样拒绝采样详细流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                    随机采样拒绝采样详细流程                          │
└─────────────────────────────────────────────────────────────────────┘

输入:
  draft_tokens:     [batch_size, max_spec_len]
  draft_probs:      [batch_size, max_spec_len]  (每个draft token的概率)
  target_probs:     [batch_size, max_spec_len]  (draft token在target中的概率)
  uniform_probs:    [batch_size, max_spec_len]  (均匀随机数)
  recovered_tokens: [batch_size, max_spec_len]  (恢复tokens)

Step 1: 计算接受条件
─────────────────────────────────────────────────────────────────────
  accept_prob = target_probs / draft_probs
  accept_condition = (draft_probs > 0) & (accept_prob >= uniform_probs)

  示例:
  位置:        [0]     [1]     [2]
  draft_prob:  [0.8]   [0.6]   [0.7]
  target_prob: [0.9]   [0.3]   [0.7]
  accept_prob: [1.0]   [0.5]   [1.0]
  uniform:     [0.3]   [0.7]   [0.2]
  accept:      [✓]     [✗]     [✓]

Step 2: 找到第一个拒绝位置
─────────────────────────────────────────────────────────────────────
  first_reject_pos = 第一个 accept=False 的位置

  示例: first_reject_pos = 1

Step 3: 创建跳过掩码
─────────────────────────────────────────────────────────────────────
  should_skip = (pos > first_reject_pos) & valid
  # 注意: 第一个拒绝位置本身不跳过，而是使用 recovered_token
  #       只有第一个拒绝位置之后的才跳过

  示例:
  位置:        [0]     [1]     [2]
  should_skip: [No]    [No]    [Yes]
               ↑       ↑       ↑
               接受    拒绝但   跳过
               draft   使用recovered

Step 4: 选择最终tokens
─────────────────────────────────────────────────────────────────────
  - 接受的位置: 使用 draft_token
  - 第一个拒绝位置: 使用 recovered_token
  - 跳过的位置: 保持原值 (PLACEHOLDER)

  示例:
  位置:        [0]     [1]     [2]
  draft:       [A]     [B]     [C]
  recovered:   [X]     [Y]     [Z]
  输出:        [A]     [Y]     [-]

Step 5: 填充bonus token
─────────────────────────────────────────────────────────────────────
  if (没有拒绝 或 最后拒绝位置 >= draft数量):
      在 draft数量 位置填入 bonus_token

  示例 (全部接受):
  位置:        [0]     [1]     [2]     [3]
  draft:       [A]     [B]     [C]     -
```

## 8. 常见问题

### Q1: 为什么 Draft Model 要比 Target Model 小？

**A**: Draft Model 的作用是快速生成候选，它的推理速度决定了投机解码的效率上限。一个小的 Draft Model（如 7B）比大模型（如 70B）快 5-10 倍，即使只有部分 token 被接受，整体吞吐量也能显著提升。

### Q2: 如果 Draft Model 的猜测全错怎么办？

**A**: 即使全部猜错，投机解码也能保证输出质量。最坏情况下：
- 贪婪采样：第一个 token 就被拒绝，使用 Target 的输出
- 随机采样：每个位置都可能被拒绝，用 recovered token 替代

这确保了输出**永远不会比 Target Model 单独推理差**。

### Q3: Bonus Token 是什么？为什么需要它？

**A**: 当所有 Draft Token 都被接受时，我们"免费"获得了一个额外的验证机会。Target Model 在验证最后一个 Draft Token 时，同时也计算了下一个位置的概率分布，我们可以直接从中采样一个 Bonus Token，而不需要额外推理。

### Q4: Block Verify 真的更好吗？

**A**: 不一定。Block Verify 的优势在于：
- 当 Draft Model 质量较好时，可以提高接受率
- 向量化实现更高效

但在某些情况下，传统方法可能更稳定。vLLM 的策略是：
- `max_spec_len < 3`: 使用传统方法
- `max_spec_len >= 3`: 使用 Block Verify

### Q5: N-gram 模式是什么？

**A**: N-gram 模式不需要 Draft Model，而是使用简单的统计规律（N-gram）来预测下一个 token。例如，如果前面是 "今天天气"，N-gram 可能会根据统计频率预测 "很"、"不错" 等。

在这种模式下，`draft_probs = None`，接受概率总是 1（因为相当于 Draft 对每个 token 的"概率"都是均匀的）。

### Q6: 为什么需要恢复分布？

**A**: 恢复分布确保最终输出的概率分布与 Target Model 完全一致。数学上可以证明：

```
P(最终输出 = x)
= P(接受 draft=x) + P(拒绝 draft) × P(recovered=x)
= p_draft(x) × min(1, p_target(x)/p_draft(x)) + ... = p_target(x)
```

这是拒绝采样的核心保证。

投机解码通过"预测-验证"的方式，在不牺牲输出质量的前提下，显著提高了大语言模型的推理效率。拒绝采样是实现这一目标的关键算法，它通过数学上严格的方法确保最终输出完全符合 Target Model 的分布。
